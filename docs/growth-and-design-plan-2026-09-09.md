# Skill Supermarket：增长与视觉的四周迭代方案

日期：2026-09-09。范围：真实数据复盘、公开资料调研、首页视觉审查和执行方案。本轮未改运行时代码、未部署、未修改自动化、未对外发送推广。以下目标是建议的实验决策门槛，不是流量或收入预测。

## 结论先行

现在最需要验证的不是“还能加什么功能”，而是：**一位正在选择 Skill/MCP 的开发者，是否愿意用我们的报告完成一次真实的采用决策。**

目前有可用的评测基础，但尚未证明稳定的目标用户触达；页面又把实际价值藏在大标题、重复卡片和长滚动之后。增长和设计应围绕同一条链路：具体任务 → 真实报告 → 理解证据 → 决定下一步 → 有新问题时回来。

未来四周先做“小而清楚的采用决策工具”，不同时做大全目录、媒体、社区和企业安全平台。先争取 10 位明确有需求的外部试用者，观察其中至少 3 位是否自愿评测自己的项目、至少 2 位是否在后续另一日因真实需求再次使用；达不到就定位断点，不用增加库存或发版次数补成绩。

## 3. 聚焦谁，为他完成什么事

**首批目标用户**：中文开发者，已经在用 Claude Code / 类似 Agent，近期正准备接入一个具体 Skill 或 MCP；不是泛 AI 围观者。

首个场景沿用现有 GitHub/浏览器自动化选型内容，从“这个工具能做什么、会碰哪些数据、是否适合我的任务”入手。访谈若显示另一场景更集中，再换一个，不同时铺十个行业。

候选定位：**安装 Skill / MCP 前，先看懂它会做什么。**

配套说明：用真实报告解释工作流程、权限与风险证据，帮你决定是否采用、如何限制权限，以及先修什么。以上是待验证的文案方向，不承诺自动证明安全。

两种入口不要混淆：

- 使用者先看现有公开报告，能完成选型就已经获得价值；不为统计注册强迫其重新评测。
- 有自己项目或不同版本的人再进入登录、评测和结果。保留来源输入、清楚说明为什么登录及会消耗什么额度。

维护者作为第二顺位：只有观察到“报告指出问题 → 修复 → 想看变化”的真实需求，才把修复前后比较作为下一项产品；不立即另建作者社区或企业功能。

## 4. 增长渠道：先跑通一个，再放大

### 第一优先：小范围、有同意的任务试用

每周争取 3–5 位有近期选型任务的人，累计先做 10 位。来源优先为已有开发者关系、允许招募试用的技术社区，以及主动寻求选型帮助的人；不爬取联系方式、不批量私信、不伪装普通用户。

邀请的价值是“用你的真实任务，给你一份可核对的选型/风险解释”，不是“帮忙点个赞”。只使用公开项目，拒绝索要公司密钥或私有代码。试用不要求好评，不以奖励诱导注册或多跑评测。

每次约 15 分钟，记录匿名编号、任务、当前替代方法、入口、卡住位置、报告是否改变决定、是否自愿评测，以及原话。展示页面前先问现在怎么选，避免诱导需求；测试中不代点按钮。反馈不自动变为可公开推荐语。

**决策门槛**：前 5 位中若不足 4 位能自行说清网站用途，先改承诺与首屏；10 位中若不足 3 位认为证据影响了其决策，先改报告价值/场景，不扩大推广。它们是小样本产品门槛，不是统计显著性结论。

### 第二优先：少量可传播的真实案例

先把既有指南与一个对应报告做成完整案例；有反馈后再补第二个。候选问题：

1. Claude Code 接 GitHub：哪些权限是任务需要的，哪些可以不授予？优先改进现有文章，避免重复 URL。
2. 浏览器自动化工具怎么选：登录态、外部页面输入、截图/文件能力各有什么边界？仅在实际核验候选后发布对比。
3. 某个报告告警如何核对、修复和复评？有真实修复前后证据才写，不造案例。

每个案例有一个明确任务、固定版本或 commit、来源、简明图示、限制和下一步。不能仅把 README 改写成推荐，也不把推断图称为运行时实测轨迹。

作者合作先从最多 3 个高度相关项目核对报告，若作者认为有用且愿意，再提供可选徽章。徽章显示报告时间/版本并链接原报告，不暗示认证，不要求交换外链。高 Star 不自动等于匹配受众；暂不批量向 30–50 个仓库开 Issue。

已备好的 [Awesome MCP DevTools 单项 PR](distribution/2026-09-09-mcp-devtools.md) 可作为一个分发实验，但目前仍待具体发送授权。一个 PR 被合并是曝光条件，不是用户增长成果。

### 并行基础工作：弄清搜索到底卡在哪里

取得站点所有者提供的 Search Console 只读数据或导出：重点 URL 索引状态、未索引原因、sitemap 状态、查询词、展现和点击；没有数据就记为未知。百度、Bing 按同样方法处理，不把平台提交成功算成收录。

旧 Vercel 站的永久重定向仍需核实真实响应与项目权限；有问题再处理。不要把过去未证实的状态当作当前已修好。Google 明确说明 sitemap 提交只是提示，不能保证抓取。[官方说明](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

一周没有自然点击，不足以否定 SEO 内容；先分开看发现/索引/展现/点击。页面发布后按 28 天窗口复盘搜索变化；有展现但无点击时再调整标题/意图，有访问但不解决问题才改正文。

### 暂不投入

不同时铺 Product Hunt、HN、多个中文社区与 Reddit；不先买广告；不批量生成年度榜单；不增加只为提升库存的采集；不靠自动邮件催用户回访。公开发布须先核对对应社区规则和 AI 内容要求，并按既有边界确认具体目标与内容。

## 6. 视觉方向：清爽、有辨识度的开发者选型工作台

保留橙色标识、暖白底与深色文字，不重新折腾品牌。变化来自内容组织：**少一些通用宣传，多一些能看懂的真实产出。** 这是方向建议，不是本轮已制作或上线的新设计。

- 首屏：桌面左侧为具体承诺、任务入口与“查看真实报告”主动作；右侧用现有报告的一段真实流程图、结论和证据摘要。手机按“用途 → 主动作 → 简明样例”排列。评测自有项目作为清楚的次动作，不与搜索、方法说明争抢第一注意力。
- 图示：展示真实数据，带项目名、报告日期和推断边界。线性/分支步骤用流程图；多主体交互用时序图；组件关系才用结构图。没有足够关系就用文字，不为漂亮编造流程。移动端允许图自身平移/放大并提供文本等价内容，不让整页横滑。
- 主体：三个具体任务入口 → 一份展开的案例 → 少量可扫描的目录行 → 方法与局限。不是“标题、四张卡、标题、四张卡”循环。
- 报告：先回答用途、关键风险/证据不足、下一步；评分退为辅助。证据、图和原始来源能按需展开。不能用绿色大分数覆盖严重风险，也不能因为数据缺失一律写成危险。
- 排版：中文正文可读性优先，建立标题/结论/证据/元数据四级；只在路径、版本等内容使用等宽字，不为了区别而下载多套大字体。日期与证据重要，但视觉权重低于结论。
- 动效：只用于展开、筛选、复制、加载状态；不加背景粒子、自动轮播、无意义的闪动。真实变化来自内容更新，不是假装实时的装饰。
- 手机验收：320/375/390/414/768px 可完整阅读，图不挤破页面，键盘可操作；1280×800 中用途、主动作与真实样例核心内容不需滚动即可看到。保留空态、长标题、错误态和 reduced-motion，实测颜色对比度。

首轮改版只动首页与案例呈现；不顺带重写登录、管理后台、评测引擎或整个设计系统。两张静态设计草案可用于小范围理解测试，选定后交付一套生产实现，不维护两套长期 A/B 页面。

## 7. 四周路线：一个主假设，产品与触达一起做

日期是计划，不是承诺外部用户或平台按时配合。责任主体：我负责实现、验证、素材、复盘；账号持有人处理第三方账户开通/所有权验证，并确认具体对外发送。不能因此把全部增长工作停下。

| 周期 | 唯一主假设 | 产品交付与触达动作 | 检查与停止条件 |
| --- | --- | --- | --- |
| 第 1 周，9/9–9/15 | 新访客先看懂一次真实用途，才会愿意继续 | 完成首页首屏重排、修复额外空白、突出一份合适的真实样例；组织首批 5 人任务试用；取得搜索后台数据或明确权限缺口。已有单项 PR 按授权推进 | 5 人中争取 4 人不经解释说清用途、找到报告与一条证据；不足则调整表达。无访客就优先做邀请，不能继续加首页装饰 |

| 第 3 周，9/23–9/29 | 修复或版本变化会产生复用需求 | 只有前两周出现明确需求才做报告前后差异/同项目复评入口；邀请已同意回访的人检查实际新任务。若主要阻力仍是首次使用，继续解决它，不机械进入留存功能 | 观察至少 2 位在另一日因真实需求返回；若无人有复用任务，不用邮件制造活跃，也不投入复杂通知/订阅系统 |
| 第 4 周，9/30–10/6 | 有一个渠道能持续带来有用的目标访问 | 只扩大前期有证据的一个渠道；补第二个真正被需要的案例；取得愿意合作作者的报告反馈；访谈重复用户付费工作需求 | 按渠道看真实试用与首次价值；没有可重复信号就保持小规模并调整定位，不启动全平台发布或广告。收费开发须有重复需求再评估，定价/支付另行确认 |

## 8. 如何防止再跑偏

每周固定一次决策复盘，其他迭代围绕同一问题完成；不要求每个心跳都换题或为了有提交而改代码。

1. 先读上轮假设、发布版本和用户证据。未完成的核心工作继续到可验证，不重新选技术小修。
2. 一次只设一个主实验：用户是谁、卡在哪里、做哪一项、如何看到效果、何时停止。每项功能必须写出“帮谁完成哪一步”。
3. 每周同时留出真实接触/分发与产品工作的时间。建议约 40% 用户研究和分发、40% 首次价值与视觉、20% 质量运维；这是防偏分配而非硬 KPI，严重故障/安全事件可打断。
4. 技术安全、测试和部署是门槛；新增回归数量、采集数、内部评测数和提交次数都不进入增长成绩。
5. 连续两轮没有新用户证据时，不新增功能清单。触达没发生就处理渠道/招募；人来了但不理解就改承诺；理解但觉得没用就改问题/报告；真正有用却无法完成就修链路。

最小周报只保留：**接触了谁（脱敏）→ 解决了什么 → 有多少人自愿继续/回来 → 本周改变了什么 → 下周只做什么**，另列故障与必要支持。不用大段健康巡检占据产品周报。

### 最小指标表

| 层次 | 记录方式 | 当前可用性 |
| --- | --- | --- |
| 触达 | 经同意试用人数、来源、目标任务；搜索展现/点击另列 | 试用记录待建立；搜索后台待取得 |
| 首次价值（短期主指标） | 外部试用者在真实任务中读到证据，并能说明决定/下一步；按匿名研究编号去重 | 当前未知，先人工核实，不把点击自动判成“有效决策” |
| 自助使用 | 排除运营/自测后的首次完成评测用户，报告访问/证据展开作为代理行为单列 | 后端任务已有；部分前端行为缺失，确有决策需要再补最小事件 |
| 复用 | 已首次获得价值的人，在另一日因真实需求回来；满 7 天的人单列观察窗口 | 不能把当前一个账号的重复任务直接称为客户留存 |
| 商业信号 | 愿意进一步讨论持续工作流/团队需求的人及具体问题；付费以实际订单为准 | 订阅 0；意愿尚未访谈 |

拒绝统计的访客继续尊重 DNT/GPC，不用设备指纹拼接匿名用户；无同意身份关联时只报告聚合事件。不得用不同口径的 PV、注册和任务直接相除。小样本同时报原始计数与原话，不报“提升 300%”等误导比例。

## 9. 上线门槛与依赖

- 实现前读取本项目对应版本 Next.js 指南；保留真实报告、缺失数据与风险边界。报告截图/图示不得使用虚构分数、背书或用户评价。
- 上线前执行 typecheck、lint、相关测试、生产 build，以及首页、报告、登录返回路径、SEO 和断点的实际浏览器验证；检查首屏而非只检查无溢出。功能产生的新增网络请求、前端包大小和关键页面性能需有前后记录，拒绝装饰导致的明显退化。
- 算法不随视觉修改调整；若用户证据要求算法修复，独立建立固定样本基线与回归，不凭审美改分。
- 生产目前与 main 存在有意隔离：未开通服务的验证码/邮箱注册保护不得被顺带发布。正式启用前需服务端校验、一次性验证码/过期/尝试次数/限流、防账号枚举、邮件实际送达及异常路径验收；不是仅增加一个前端框。
- 邮件服务未开通不阻塞公开报告、选型内容和少量经同意试用；也不能因此绕过现有额度/风控或放开无限匿名评测。大规模公开拉新前先闭合注册防滥用与邮件依赖。
- 应用发布沿用“已验证提交 + 免密 SSH + 可读备份 + release 回滚”门槛，不将调研文档打包成无意义发版。
- 对外 PR、帖子、评论、私信和邮件：内容与目标确定后再确认；不冒用用户身份、不自动群发。新账户开通、支付与重大权益变动按既有边界另行确认。

## 下一次实际实现只做这一项
