## 2. 三种产品的可借鉴机制与不可推导事项

### skills.sh：动作与审计相邻，但不是安全承诺

[官方文档](https://www.skills.sh/docs)把安装动作直接放在起步处；[审计列表](https://www.skills.sh/audits)并列三个供应商的结论，也存在 Pending 和彼此不同的风险结果。由此可以确认“其他目录都没有安全评测”不成立，但不能推断每一项都完成审计、不同服务使用同一证据或哪一个判断更准确。

对本站的启发是把实际结果放在采用链路里，不是新增一个装饰性安全徽章。没有足够真实用户流量时，不模仿安装榜单或用下载数制造可信度。本轮没有复制对方文案、样式或评分。

### OpenSSF Scorecard：先选择使用方式，再解释结果

[官网](https://scorecard.dev/)提供手动 CLI 与维护者 Action 两类路径；[逐项说明](https://github.com/ossf/scorecard/blob/main/docs/checks.md)把风险、评分依据、修复和适用局限连接起来。这类机制让“第一次拿到结果”和“长期接入”不必同时完成。

本站已有独立 SDK 和制品，无需再开发一个 CLI、Action 或全新服务。先从已发布包获得离线报告，之后才考虑宿主系统、队列和 AI。对方官网估计的安装时长不是本站性能证据；其 token 权限指引也不能照搬到无需 token 的离线路径。

### Socket：详细公式仍有证据边界

[官方评分文档](https://docs.socket.dev/docs/package-scores)解释多类告警和项目属性如何影响分数，同时提示文档与部署可能不同。本站不应因为公开了权重，就声称自己的判断可以完全替代其他工具。

对应到首次报告，必须解释：低置信度是证据限制；AI disabled 时不出 AI 图示；空建议数组并非无需审查。只验证这几个字段与已发布制品一致，不调整权重或借用对方算法来提高分数。

## 3. 唯一进入交付的机制

**“先有一份可解释结果，再决定完整集成”。** 面向已经来到代码仓库、希望本地预检文档的开发者；不是替换当前网站目标用户，也不把 SDK 下载当作网站注册。

- 根 README 明确指向已公开的固定安装包，不再让普通消费者先打包整站。
- [首次报告指南](../sdk-first-report.md)覆盖校验制品、运行包内虚构样例、替换为指定本地 README、解释结果和错误退出。一次仅处理显式选定的文件，不递归扫描或执行待测内容。
- 不建新包、不增 API、不覆盖 SDK 1.0.0 资产、不加入遥测、不发布第三方推广。本轮不再增加网页 release 和服务器磁盘占用。
- 真实未知元数据保留未知；单份 README 预检不是完整仓库扫描，更不是安全认证。

成功的交付指标是照文档原样可以完成隔离安装并取得正确标记的报告，失败输入明确失败。业务验证仍需真实使用反馈、排除验收的资产下载等外部信号；当前都不能证明增长。
