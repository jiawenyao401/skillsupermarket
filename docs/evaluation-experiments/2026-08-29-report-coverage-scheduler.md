# 有界报告覆盖调度：2026-08-29

目标：在不抢占用户评测、不改变评分算法的前提下，逐步为高影响、可核验的 GitHub 项目补齐评测报告。

## 基线与假设

北京时间 2026-08-29 16:27 的生产汇总：179 个有效项目中 24 个有报告，覆盖率 13.4%；近 7 天用户评测 8 次、完成率 100%。当前瓶颈不是任务成功率，而是多数详情页没有可解释报告。

可证伪假设：每 6 小时最多调度 3 个无报告项目，并让用户任务始终排在后台任务之前，可在 7 天内把报告覆盖率提升到至少 35%，同时保持用户评测完成率不低于 95%。

## 约束

- 只选择 active、具备 GitHub 仓库、没有历史报告且没有 active job 的项目。
- 优先补齐 GitHub Stars 较高的项目，使有限 Judge 成本先服务高访问潜力页面。
- 每轮默认 3 个、硬上限 5 个；`EVALUATION_COVERAGE_BATCH=0` 可立即暂停，无需重新部署。
- 后台任务最多尝试 2 次；用户任务、用户兼容任务、案例任务和普通运维任务均优先于覆盖任务。
- 原子插入并复用 active-job 唯一索引，避免流水线与用户提交并发时创建重复任务。

## 成功与停止条件

7 天后比较报告覆盖率、scheduled-coverage 完成率和用户任务完成率。若用户任务完成率低于 95%、后台任务失败率超过 10%，或出现用户任务持续等待超过 1 分钟，则将批量设为 0 并定位 Worker、上游 API 或 Judge 根因；不得通过增加重试掩盖故障。
